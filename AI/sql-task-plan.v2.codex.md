# SQL Task Plan v2 (Preparation-Only)

Этот документ задаёт операционально точный workflow подготовки SQL-задачи в репозитории.
Цель: подготовить окружение, схему, данные и контур проверок без реализации финального SQL-решения.

## 1) Режимы работы и правило переключения

### `Preparation mode` (режим этого документа)
- Разрешено: инфраструктура, миграции, сидирование/загрузка данных, подготовка `solution.sql` как заготовки, smoke-check.
- Запрещено: финальный SQL-ответ и доведение логики `solution.sql` до корректного решения задачи.

### `Execution mode` (вне этого документа)
- Используется только если пользователь явно просит решить задачу.
- В этом режиме применяется отдельный execution-процесс, а не текущий preparation-plan.

### Mode switch rule
- Если входной запрос явно содержит намерение "решить задачу / дать финальный SQL", нужно зафиксировать переключение в `Execution mode`.
- Если явного запроса на решение нет, оставаться в `Preparation mode`.

## 2) Parameter Binding (единые входные параметры)

Перед стартом зафиксируй только эти переменные:

- `PROBLEM`: имя папки задачи, например `second_highest_salary`
- `DIR`: `sql/${PROBLEM}`
- `SOLUTION_FILE`: `${DIR}/solution.sql`

Пример binding:

```bash
PROBLEM=second_highest_salary
DIR=sql/${PROBLEM}
SOLUTION_FILE=${DIR}/solution.sql
```

Gate-check:
- Директория `${DIR}` существует.
- Файл `${SOLUTION_FILE}` существует.

Stop-condition:
- Если `${DIR}` или `${SOLUTION_FILE}` отсутствуют, выполнение останавливается до исправления структуры.

## 3) Подготовка окружения БД

Команды:

```bash
make up
make ps
```

Gate-check:
- Сервис PostgreSQL в состоянии `running`.

Stop-condition:
- Если БД не поднялась, дальнейшие этапы запрещены.

## 4) Приведение схемы к актуальному состоянию

Команды:

```bash
make migrate-status
make migrate-up
make migrate-status
```

Gate-check:
- Повторный `make migrate-status` не показывает неприменённых миграций.

Stop-condition:
- Любая ошибка миграций или неконсистентный статус блокирует дальнейшие шаги.

## 5) Decision Table для загрузки данных

Выбор делается строго по таблице:

| Условие | Действие | Decision path |
|---|---|---|
| Есть рабочий сидер для `PROBLEM` | `make seed PROBLEM=${PROBLEM}` | A |
| Сидера нет, но есть `setup.sql` и/или `test_data.sql` | Запуск через `make sql-run FILE=...` | B |
| Нет ни сидера, ни SQL-файлов подготовки | Остановить процесс | BLOCKED |

Проверки наличия файлов для path B:
- `${DIR}/setup.sql` (опционально)
- `${DIR}/test_data.sql` (опционально)
- Минимум один из них должен существовать.

Команды для path B (выполнять только для существующих файлов):

```bash
make sql-run FILE=${DIR}/setup.sql
make sql-run FILE=${DIR}/test_data.sql
```

Gate-check:
- Все выполненные команды завершены с `exit code 0`.
- Есть подтверждение, что данные загружены (контрольный `SELECT` через `make db-shell` при необходимости).

Stop-condition:
- Ошибка загрузки или отсутствие любого допустимого пути загрузки (`A`/`B`) блокирует этап подготовки.

## 6) `solution.sql` как заготовка (без решения)

Обязательные требования к `${SOLUTION_FILE}`:
- Файл существует.
- В файле сохранён корректный `search_path` для целевой схемы (если используется в проекте задачи).
- В файле есть только placeholder-заготовка.

Разрешённый placeholder (пример):

```sql
-- TODO: implement final query in Execution mode.
SELECT 1 AS placeholder;
```

Запрещённые признаки:
- Завершённая бизнес-логика решения.
- Конструкции, явно закрывающие условие задачи (например, релевантные задаче агрегаты/оконные функции/ранжирование/фильтрация финального ответа).

Gate-check:
- Файл валиден как заготовка и не содержит финального решения.

Stop-condition:
- Если найден финальный ответ, preparation-процесс считается нарушенным и останавливается.

## 7) Строгая проверка детерминированности

Цель: доказать воспроизводимость подготовительных данных.

Протокол (минимум 2 прогона):
1. `reset/clean` состояния задачи (повторное приведение схемы и пере-загрузка данных).
2. `load` данных выбранным path (`A` или `B`).
3. `control`-проверка: один и тот же контрольный запрос/чексумма результата.
4. Повторить шаги 1-3 второй раз.
5. Сравнить результаты контроля между прогонами.

Допустимый формат control-проверки:
- Контрольный `SELECT` с фиксированным `ORDER BY`.
- Или checksum по детерминированной выборке (например, `md5(string_agg(... ORDER BY ...))`).

Критерий успеха:
- Контрольный результат прогона #1 идентичен прогону #2.

Критерий провала:
- Отличие контрольных результатов между прогонами.
- Ошибка любого шага протокола.

## 8) Финальная валидация готовности

Основной smoke-check (обязательный):
- БД поднята.
- Миграции актуальны.
- Данные грузятся стабильно выбранным `Decision path`.
- Подготовительные SQL-файлы (если есть) исполняются без ошибок.
- `${SOLUTION_FILE}` остаётся placeholder-заготовкой.

Дополнительный check (опционально):

```bash
go test ./...
```

Правило интерпретации:
- Падение `go test ./...` не блокирует SQL preparation, если падение нерелевантно текущей SQL-задаче и это явно зафиксировано в отчёте.

Stop-condition:
- Если обязательный SQL smoke-check не проходит, этап подготовки не закрывается.

## 9) Завершение работы

Команда:

```bash
make down
```

Gate-check:
- Локальное окружение остановлено или явно зафиксирована договорённость оставить его запущенным.

Stop-condition:
- Нельзя оставлять окружение в неявном состоянии.

## 11) Быстрый чеклист готовности

- [ ] Режим зафиксирован (`Preparation mode` / `Execution mode`)
- [ ] Входные переменные (`PROBLEM`, `DIR`, `SOLUTION_FILE`) подтверждены
- [ ] БД поднята и доступна
- [ ] Миграции применены
- [ ] Данные загружены по `Decision path` A или B
- [ ] Детерминированность подтверждена (2 идентичных контрольных прогона)
- [ ] `${SOLUTION_FILE}` подготовлен как placeholder (без финального ответа)
- [ ] Обязательный SQL smoke-check пройден
- [ ] Финальный отчёт заполнен
