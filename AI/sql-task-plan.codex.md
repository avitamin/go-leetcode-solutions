# Детальный Default Task Plan для SQL-задач

Этот документ описывает базовый workflow для любой SQL-задачи в репозитории.
Основной режим работы: через Docker Compose и Make-команды проекта.

## Критически важное правило

Ни при каких условиях не решать задачу в рамках этого плана.

- Нельзя писать финальный SQL-ответ.
- Нельзя дорабатывать логику `solution.sql` до корректного решения.
- Цель плана: только подготовить инфраструктуру, схему, данные и проверочный контур, чтобы решение можно было выполнить позже.

## 0) Входные параметры задачи

Перед стартом зафиксируй:

- `PROBLEM`: имя папки задачи (пример: `second_highest_salary`)
- `DIR`: путь к SQL-директории (пример: `sql/second_highest_salary`)
- `SOLUTION_FILE`: основной SQL-файл (пример: `sql/second_highest_salary/solution.sql`)

Gate-check:

- Папка `sql/<problem_name>/` существует.
- Внутри есть как минимум `solution.sql`.

Stop-condition:

- Если директория или `solution.sql` отсутствуют, не переходи дальше.

## 1) Подготовка окружения БД

Команды:

```bash
make up
make ps
```

Ожидаемый результат:

- Контейнер PostgreSQL запущен и находится в состоянии `running`.

Gate-check:

- `make ps` показывает активный сервис БД.

Stop-condition:

- Если БД не поднялась, следующие этапы запрещены.

## 2) Приведение схемы в актуальное состояние

Команды:

```bash
make migrate-status
make migrate-up
make migrate-status
```

Ожидаемый результат:

- Все миграции применены без ошибок.
- Повторный `migrate-status` не показывает неприменённых миграций.

Gate-check:

- Схема БД соответствует текущему набору `migrations/`.

Stop-condition:

- Если миграции не применились или статус неконсистентный, дальнейшие шаги запрещены.

## 3) Подготовка данных для проверки SQL

Вариант A (предпочтительный, если есть сидер):

```bash
make seed PROBLEM=<problem_name>
```

Вариант B (если задача работает через SQL-файлы setup/test_data):

```bash
make sql-run FILE=sql/<problem_name>/setup.sql
make sql-run FILE=sql/<problem_name>/test_data.sql
```

Ожидаемый результат:

- Тестовые данные загружены в целевую схему без ошибок.

Gate-check:

- Команды завершаются успешно (exit code 0).
- Данные явно присутствуют (например, через контрольный `SELECT` в `db-shell` при необходимости).

Stop-condition:

- Если данные не загрузились, решение не валидируется.

## 4) Подготовка файла решения (без реализации логики)

Проверки:

- `sql/<problem_name>/solution.sql` существует.
- В файле сохранён корректный `search_path` для целевой схемы.
- В файле есть безопасная заготовка/комментарий для будущего решения.

Ожидаемый результат:

- Файл готов к дальнейшей работе, но не содержит финального ответа задачи.

Gate-check:

- Нет признаков завершённого решения.

Stop-condition:

- Если в `solution.sql` уже внесён финальный ответ, этот план считается нарушенным и должен быть остановлен.

## 5) Детерминированность подготовительных SQL-файлов

Команды:

```bash
make sql-run FILE=sql/<problem_name>/setup.sql
make sql-run FILE=sql/<problem_name>/test_data.sql
```

Ожидаемый результат:

- Подготовительные файлы выполняются без ошибок.

Gate-check:

- Состояние данных после `setup.sql` и `test_data.sql` воспроизводимо.

Stop-condition:

- Если подготовительные файлы нестабильны или зависят от неявного порядка, задача не готова к этапу решения.

## 6) Финальная валидация готовности (без проверки правильности ответа)

Обязательные проверки:

- Схема применена и актуальна.
- Тестовые данные загружаются стабильно.
- `solution.sql` присутствует как заготовка и готов к последующей реализации.

Рекомендуемая команда для smoke-check:

```bash
go test ./...
```

Ожидаемый результат:

- Go-тесты проходят или есть явное объяснение, почему они не относятся к текущей задаче подготовки.

Gate-check:

- Нет блокеров в инфраструктуре/данных перед началом этапа решения.

Stop-condition:

- Если окружение неготово, этап подготовки не закрывается.

## 7) Завершение работы

Команда:

```bash
make down
```

Ожидаемый результат:

- Локальное окружение аккуратно остановлено.

Gate-check:

- Сервис БД остановлен или оставлен осознанно (если есть договорённость по команде).

Stop-condition:

- Не оставляй окружение в неявном состоянии.

## Шаблон финального отчёта по задаче

Используй этот шаблон в итоговом сообщении:

```md
## SQL Task Report: <problem_name>

### Что сделано
- ...

### Какие команды запускались
1. `make up`
2. `make migrate-up`
3. ...

### Результаты проверок
- `make sql-run FILE=.../setup.sql`: <успех/ошибка + краткий вывод>
- `make sql-run FILE=.../test_data.sql`: <успех/ошибка + краткий вывод>
- `go test ./...`: <успех/ошибка + комментарий>

### Риски / что осталось
- Что именно ещё нужно сделать на этапе реализации решения (но без самого решения в этом плане)
```

## Быстрый чеклист "готово"

- [ ] БД поднята и доступна
- [ ] Миграции применены
- [ ] Данные загружены
- [ ] `solution.sql` подготовлен как заготовка (без финального ответа)
- [ ] Подготовительные SQL-файлы (`setup.sql`, `test_data.sql`) воспроизводимы
- [ ] Инфраструктура готова к отдельному этапу решения
- [ ] Подготовлен финальный отчёт
