# Algorithmic Task Plan v1 (Preparation-Only)

Этот документ задаёт операционально точный workflow для подготовки алгоритмической задачи в Go.
Цель: подготовить структуру задачи, сигнатуру, автотесты и проверочный контур без реализации финального алгоритма.

## 1) Режимы работы и правило переключения

### `Preparation mode` (режим этого документа)
- Разрешено: создание/проверка структуры файлов задачи, подготовка `solution.go` как заготовки, генерация `solution_test.go` по условиям пользователя, запуск тестов для проверки контура.
- Запрещено: реализация алгоритма решения задачи в `solution.go`.

### `Execution mode` (вне этого документа)
- Используется только если пользователь явно просит реализовать решение.
- В этом режиме применяется отдельный execution-процесс, а не текущий preparation-plan.

### Mode switch rule
- Если входной запрос явно содержит намерение «реши задачу / напиши алгоритм», фиксируется переключение в `Execution mode`.
- Если явного запроса на реализацию нет, оставаться в `Preparation mode`.

## 2) Input Contract (что обязательно получить от пользователя)

Перед стартом зафиксируй:

- `PROBLEM`: имя задачи в `snake_case` (пример: `two_sum`)
- `FUNCTION_NAME`: имя экспортируемой или неэкспортируемой функции решения (пример: `twoSum`)
- `SIGNATURE`: точная сигнатура функции (пример: `func twoSum(nums []int, target int) []int`)
- `EXAMPLES`: минимум 2 примера из условия (`input -> expected output`)
- `CONSTRAINTS`: ограничения (размеры, диапазоны значений, спец-условия)

Gate-check:
- Все поля выше заданы явно.
- Форматы входа/выхода не противоречат друг другу.

Stop-condition:
- Если не хватает сигнатуры или ожидаемых результатов примеров, процесс останавливается до уточнений.

## 3) Parameter Binding (единые пути)

Зафиксируй переменные:

- `DIR`: `problems/${PROBLEM}`
- `SOLUTION_FILE`: `${DIR}/solution.go`
- `TEST_FILE`: `${DIR}/solution_test.go`

Команды:

```bash
mkdir -p "${DIR}"
```

Gate-check:
- Директория `${DIR}` существует.

## 4) Подготовка `solution.go` как заготовки (без решения)

Создай или обнови `${SOLUTION_FILE}`:

- Пакет должен совпадать с пакетом задачи в директории.
- Функция с именем `FUNCTION_NAME` и точной сигнатурой `SIGNATURE` присутствует.
- Внутри только безопасный placeholder (без алгоритма), например:
  - `panic("TODO: implement")`, или
  - возврат нулевого значения + `TODO`-комментарий.

Строгий запрет:
- Нельзя добавлять рабочую логику, проходящую тесты задачи.
- Нельзя вставлять частичное «почти-решение».

Gate-check:
- Файл компилируется (или даёт предсказуемый runtime-fail из-за `panic("TODO")`).
- Нет признаков реализованного алгоритма.

## 5) Генерация `solution_test.go` из условий пользователя

Сгенерируй `${TEST_FILE}` в table-driven стиле и разбей тесты на группы.

### Группа A: Canonical examples
- Каждый официальный пример из `EXAMPLES` должен быть отдельным тест-кейсом.
- Expected values должны совпадать с условием один-в-один.

### Группа B: Constraint-boundary tests
Добавь граничные тесты на основе `CONSTRAINTS`, например:
- минимальные размеры входа;
- максимальные размеры входа (в разумных для unit-теста пределах);
- минимальные/максимальные значения элементов;
- дубликаты, отрицательные значения, нули, если допустимо.

### Группа C: Special-case behavior
Покрой явно заявленные специальные правила из условия:
- «всегда есть ответ / ответа может не быть»;
- «индексы уникальны / порядок важен / порядок не важен»;
- «разрешены повторяющиеся элементы» и т.д.

### Нормализация сравнений
- Для срезов/коллекций учитывай правило задачи: порядок важен или нет.
- Если порядок не важен, нормализуй сравнение в тесте (сортировка копий, map-count, set-проверка).
- Для `float` используй epsilon-сравнение при необходимости.

Gate-check:
- Тесты детерминированы и не флапают.
- В тестах нет «подсказки-решения» (например, дублирования полноценного алгоритма внутри теста).

## 6) Команды валидации контура

Запусти проверки:

```bash
go test ./...
```

Ожидаемое поведение в `Preparation mode`:
- Тесты задачи могут падать из-за placeholder-реализации — это допустимо.
- Критично, чтобы тесты компилировались и корректно запускались.

Дополнительно (по возможности):

```bash
go test ./... -run <ProblemOrFunctionPattern>
```

Gate-check:
- Нет ошибок компиляции в созданных/изменённых файлах.
- Падения тестов объяснимы отсутствием реализации, а не ошибками подготовки.

Stop-condition:
- Если тесты не стартуют из-за синтаксиса/импортов/несовместимой сигнатуры, этап подготовки не закрыт.

## 7) Definition of Done (Preparation)

Этап подготовки считается завершённым, если:

- Создана/проверена папка `problems/${PROBLEM}`.
- `${SOLUTION_FILE}` содержит только заготовку с корректной сигнатурой.
- `${TEST_FILE}` содержит автотесты по примерам, границам и спец-правилам из условия.
- Тестовый контур компилируется и запускается.
- В отчёте явно зафиксировано, что реализация алгоритма оставлена пользователю.

## 8) Шаблон финального отчёта

```md
## Algorithmic Task Preparation Report: <problem>

### Режим
- `Preparation mode`

### Что получено от пользователя
- Function: `<SIGNATURE>`
- Examples: `<N>`
- Constraints: `<кратко>`

### Что подготовлено
- `[problems/<problem>/solution.go](...)` — заготовка без решения
- `[problems/<problem>/solution_test.go](...)` — автотесты по условию

### Какие команды запускались
1. `go test ./...`
2. `go test ./... -run <pattern>` (если запускался)

### Результат проверок
- Компиляция: success | fail
- Запуск тестов: success | fail
- Причина падений (если есть): `<обычно TODO/panic в solution.go>`

### Что остаётся пользователю
- Реализовать алгоритм в `solution.go` без изменения контрактов тестов.
```
